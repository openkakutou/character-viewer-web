# character-viewer-web — Codebase index

## Modules
- [`modules/app.md`](modules/app.md) — application entry point: registers `web-ui-kit`'s custom elements/tokens, awaits `i18n`'s `initAppI18n()` at bootstrap (never a flash of the wrong language), then delegates all rendering to `shell`
- [`modules/shell.md`](modules/shell.md) — the launch screen → persistent workspace shell transition (item 020): full-frame first-character-load step, then a toolbar (app title/version, character name, a `<wuik-locale-switcher>`) + vertical section list (`wuik-tabs`) showing one already-loaded-and-mounted section at a time (four from `viewer`, one from `game-mode`), auto-pausing the animation player/in-game preview playback and moving focus on switch via a `MutationObserver`
- [`modules/i18n.md`](modules/i18n.md) — this app's own localization setup (item 018): wires `web-ui-kit`'s shared i18next integration layer under this app's own namespace/`localStorage` key, plus a `t()` wrapper that falls back to a plain interpolated default value before the app has initialized
- [`modules/input.md`](modules/input.md) — the character file input: folder selection only (item 015) — gathers a picked/dropped folder's files, finds its `.def` candidate(s) (auto-picking a lone one, asking the user among several via a native radio-group picker), learns which sibling files it references via a narrow local `[Files]`-section read, resolves each by basename against the folder listing, and loads the character through the WASM bridge; also renders the folder-picker + drag-and-drop UI
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `character` WASM release build
- [`modules/viewer.md`](modules/viewer.md) — screens that display an already-loaded character's data, each hosted as one section of `shell`'s workspace: the characteristics panel (name, animation/sprite counts, sorted Statedef list, item 012's author line and basename-only referenced-files list, each shown only when present), the sprite browser (item 005 — collapsed-by-default group list, on-demand pixel decode into a `<wuik-viewport>`-wrapped `<canvas>` with real zoom/pan/reset-to-fit, item 016, stale-decode discarding), the animation player (item 007 — per-frame timed playback, pause/step/loop, on-demand decode per frame, optional collision box overlay, an item-020 `pause()` handle method for auto-pause-on-navigate-away, and item 014's mounted "Export GIF"/"Export Stand" buttons from `export`), and the palette picker (item 006 — lists referenced `.act` file names, applies an uploaded override to whichever sprite/frame is currently shown)
- [`modules/export.md`](modules/export.md) — builds a downloadable animated GIF from a loaded Animation (item 014), reusing the animation player's own resolved-sprite + palette pipeline: frames are composited onto one shared, axis-point-aligned canvas (sprites differ in size across a single animation) before being quantized and encoded via the third-party `gifenc` library; "Export Stand" always targets Animation 0 (MUGEN/Ikemen's own standing-animation convention), surfacing a clear inline error instead of downloading anything when the character defines none
- [`modules/game-mode.md`](modules/game-mode.md) — the in-game preview mode (item 008): a scrollable list of one button per animation, each triggering it to play immediately and loop continuously in a shared preview stage, replacing whatever was playing; the same button stops it if clicked again while it's the one playing. Reuses `viewer`'s animation player timing/decode helpers rather than embedding its full debug UI. The Special Moves list (item 009) is a near-twin sixth section keyed by Statedef instead of animation number, resolving each state's own associated animation (or none) via its own small pure helper
- [`modules/wasm.md`](modules/wasm.md) — bridge to the `character` WASM module: loads it client-side and exposes typed wrappers — `loadCharacter` plus the `CharacterData` TypeScript vocabulary, and `resolveSpritePixels` for on-demand sprite pixel decoding (item 005) — each returning a typed result instead of throwing

## Observed patterns
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderCharacterFileInput(root, options)`, `renderCharacteristicsPanel(root, character)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap — same "inject external effects for testability" shape as the WASM bridge and download script, applied here to DOM construction instead of `fetch`; `renderApp`'s own `options.bridgeOptions` exists solely to let tests inject the same real-WASM-fixture stubs `wasm`/`input`'s own tests use, all the way through the composition root
- Any app-level visual value (typography hierarchy, spacing) is expressed only through `@openkakutou/web-ui-kit`'s `--wuik-*` CSS custom properties, never a literal px/hex value — see `.vibe/decisions/003-app-shell-adoption-scope.md`
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs` (not bundled/type-checked by `tsc`, whose `include` is scoped to `src/`)
- CLI-style scripts return an exit code from a testable `main(argv, overrides)` function rather than calling `process.exit` directly, and inject external effects (`fetch`, output dir) as parameters for testability — the same "inject external effects" shape reappears in `src/wasm/bridge.ts` (`fetchWasmExecSource`/`fetchWasmBytes`) and `src/input/character-file-input.ts` (`readFileBytes`), needed wherever jsdom can't be trusted to behave like a real browser
- `wasm_exec.js` (a plain global-side-effect script, not an ES module) is executed via `new Function(source)()` rather than a `<script>` tag or dynamic `import()`, so the same loading code works identically in a real browser and under jsdom/Node — see `.vibe/decisions/002-wasm-bridge-loading-and-result-shape.md`
- File bytes are read via `FileReader#readAsArrayBuffer` rather than `Blob#arrayBuffer()` for the same real-browser/jsdom parity reason — jsdom (as of the pinned version) does not implement `Blob#arrayBuffer()` at all, while `FileReader` works identically in both
- Fixture-driven tests that exercise the real WASM module pin expected values obtained by running the actual module once against the fixture (not derived from the same mapping code under test), copying minimal `.air`/`.sff`/`.cns` fixtures from the `character` repo's own test data into `src/wasm/testdata/` rather than depending on a sibling checkout at test time; `src/input/`'s tests reuse those same fixtures rather than duplicating them
- When a WASM boundary can't answer "what does this file reference" on its own (`character`'s `load` call needs all 4 required files' bytes at once, unlike a bridge that could parse an entry-point file alone and report its own referenced filenames), a deliberately minimal, narrowly-scoped local text parse of just the relevant section (`def-files-section.ts`'s `.def` `[Files]`-section read, 3 keys) is written instead of reaching for the format's own full parser — mirroring the source Go library's own parser's key-to-field mapping, checked directly against its source rather than guessed (item 015, `.vibe/decisions/017`)
- A referenced filename is resolved against an already-gathered folder listing by basename — exact case first, case-insensitive fallback second, more than one match reported as ambiguous rather than silently picked — ported directly from the sibling `*-editor`/`*-viewer-web` apps' own established resolution rule (`character-file-input.ts`'s `resolveReferencedFile`), not re-derived, since basename resolution has no domain specifics of its own
- A generic, domain-agnostic browser-API-workaround module (folder-selection gathering: a `webkitdirectory` picker's `FileList` plus a dropped folder's recursive `DataTransferItem.webkitGetAsEntry()`/`FileSystemDirectoryReader` walk) is ported near-verbatim from a sibling repo (`character-editor`) that already shipped and real-browser-verified the identical shape (item 015's `folder-entries.ts`), rather than re-derived — the non-standard browser types (`FileSystemEntry`, `DataTransferItem`) are modeled as minimal `*Like` interfaces covering only the members actually read, so the walk logic is unit-testable against plain mock objects even though jsdom implements neither API at all
- A `hidden`-toggled element given its own class-level `display` CSS value (`.file-input__selection { display: flex }`, item 015's multi-`.def` candidate picker) can silently lose the `hidden` attribute's effect — the UA stylesheet's `[hidden] { display: none }` and an author class selector have equal specificity, and author rules win at equal specificity — fixed with a higher-specificity `.file-input__selection[hidden] { display: none }` override, the same fix already verified in the sibling `character-editor` app
- Each `viewer` section is rendered exactly once, when the workspace shell mounts, and stays mounted for the rest of the session — switching sections toggles a `<wuik-tab-panel>`'s `hidden` attribute (`<wuik-tabs>`'s own mechanism) rather than destroying/re-rendering anything, which is what makes every section's own selection/expanded-group/playback state survive a switch with zero extra state-preservation code (item 020, superseding the earlier "stays inline" deferral in `.vibe/decisions/005`/`008` now that a real workspace shell exists to navigate between)
- A design-system component with no event for a state change it drives internally (`<wuik-tabs>` toggles `hidden` on switch but emits no `change`/`select` event) is reacted to with a `MutationObserver` on the specific attribute, not by listening for the component's own click/keydown handling — decouples from an internal implementation detail and works identically regardless of how the switch happened (mouse, keyboard) — see `.vibe/decisions/011-workspace-shell-tabs-composition-and-section-switch-detection.md`
- A layout-shell design-system component with no supported way to split two visually-adjacent parts across a parent's separate named slots (`<wuik-tabs>`'s tab-list strip and its panel content, vs. `<wuik-app-shell>`'s `sidebar`/`main` slots) is instead composed as one piece and given its own internal two-column `display: grid` from the consuming app's own stylesheet, targeting the component's shadow host directly — light-DOM CSS on a shadow host controls that host's own generated box in the flattened render tree, the same technique `<wuik-app-shell>` itself already uses for its own toolbar/sidebar/main split (`.vibe/decisions/011`)
- Preventing whole-page scroll requires a **definite** height on every ancestor in the chain (`html`/`body` → `#app` → the root layout shell), not just `min-height` — a box with only `min-height` set still grows to fit taller content, silently defeating an `overflow: auto` further down that has nothing bounded left to clip against; caught via real-browser verification; `<wuik-app-shell>`'s own `min-height: 100%` needed a page-level `height: 100%` override to close the chain (item 020)
- A custom CSS rule and the browser's native `[hidden] { display: none }` UA rule have equal specificity, so an unconditional `display: <anything>` targeting the same element(s) — including ones currently `hidden` — silently wins the cascade and defeats the native hiding; scope such a rule to `:not([hidden])` instead. Caught only by real-browser/screenshot verification, not jsdom's DOM-structural assertions, which don't compute cascaded styles (`workspace-shell__section`, item 020)
- A list of domain numbers/values reflects the loaded data faithfully (sorted for scannability, but never silently deduplicated) — same "show what the file actually contains" instinct as `input`'s error handling
- The app version shown in the UI is imported directly from `package.json` (`resolveJsonModule`), never duplicated as a literal constant — a hardcoded copy previously drifted out of sync with every release; `src/version.test.ts` pins the guarantee by reading `package.json` independently rather than through `appVersion` itself
- A long, potentially large (hundreds-of-items) list is never fully mounted into the DOM up front: `sprite-browser.ts`'s groups render collapsed, and a group's own sprite rows are only created the first time it's expanded (lazily, then kept mounted) — same instinct as decoding sprite pixels themselves only on selection, never eagerly for the whole sheet
- An async action re-triggerable by fast repeated user input (selecting a sprite before the previous selection's decode has resolved) is guarded with a monotonically increasing token compared at resolution time, so a slower, superseded response is discarded instead of overwriting a newer one's UI state — `sprite-browser.ts`'s `selectionToken`
- A rendering effect jsdom cannot exercise at all (`HTMLCanvasElement.getContext("2d")` throws rather than returning `null`, without the separate `canvas` npm package this project doesn't depend on) is factored into its own injectable function (`SpriteBrowserOptions.drawPixels`) with a real default — same "inject external effects for testability" shape as `fetch`/file-reading, but here the substitute exists because the *default* path is untestable under jsdom at all, not just undesirable to hit in a unit test; the real default is instead verified via real-browser Playwright runs (see `docs/testing.md`)
- A default effect implementation shared by two sibling components (`defaultDrawPixels`, `computeScaleToFit`) is exported from the module that first introduced it (`sprite-browser.ts`) and imported by the later one (`animation-player.ts`) rather than duplicated — same "share, don't duplicate" instinct as items 010/015 reusing item 003's WASM bridge path, extended by item 008's `game-mode/animation-triggers.ts` reusing `animation-player.ts`'s own pure timing helpers (`effectiveTickDuration`, `isBlankFrame`, `computeNextFrameIndex`) instead of embedding that sibling's whole debug UI just to get its timing logic
- A timed playback loop (`animation-player.ts`) is a self-rescheduling `setTimeout` chain, not `setInterval`: each tick reads the *current* frame's own duration before scheduling the next one, so per-frame timing that varies frame-to-frame is honored exactly, and tests drive it deterministically with `vi.useFakeTimers()`/`vi.advanceTimersByTimeAsync(...)`
- Calling `.click()` on a checkbox under this project's pinned jsdom does not reliably synthesize a `"change"` event (though it does toggle `.checked` first) — `animation-player.ts`'s toggles read `.checked` from a `"click"` listener instead, see `docs/testing.md`
- Under `vi.useFakeTimers()`, `vi.waitFor(...)` can itself advance fake time while polling, which is invisible for a component whose timer chain only starts on a later explicit action but lets one or more ticks fire non-deterministically for one that starts its own self-rescheduling loop immediately on the triggering action (`game-mode/animation-triggers.ts`, item 008) — `animation-triggers.test.ts` waits for the triggering click's own pending decode microtask with `await vi.advanceTimersByTimeAsync(0)` instead, see `docs/testing.md`

- A screen that must react to a state change owned by a sibling screen (the palette picker's active override, needed by the sprite browser and animation player; the workspace shell needing to stop the animation player's or the in-game preview's own internal timer from outside) does so via a small handle its own render function returns (`{ setPaletteOverride(bytes) }`, `{ pause() }`) rather than a full re-render or reaching into the render function's closure — each handle method re-runs or reuses an entry point the screen already had internally (`selectSprite`/`showFrame`, the existing pause-on-click logic), so no selection, expanded group, or playback state is lost. `game-mode/animation-triggers.ts` (item 008) reuses the exact same `{ pause() }` shape as the animation player for this, unifying it internally with its own "click the active button again to stop" logic rather than keeping two separate stop code paths
- A value validated against a real backend call (an uploaded `.act` file, checked via a probe `resolveSpritePixels` call against one of the character's own real sprites) is never pre-validated by a cheaper client-side proxy (e.g. a byte-length check) when the real call is just as cheap and strictly more correct — a same-size-but-wrong file would pass a length check yet still be meaningless
- An optional metadata field or section with nothing to show (item 012's characteristics-panel author line and Files section, each field's own "" after trimming, and a variable-length list built entirely of such fields) is omitted from the DOM entirely — never rendered with a blank value or a leftover empty heading — same instinct as `sprite-browser.ts`/`palette-picker.ts`'s own "nothing loaded yet" no-op renders, generalized here to per-field emptiness within an otherwise-populated screen
- A list row whose data legitimately resolves to "nothing to show" (a Statedef with no clearly associated animation, item 009's `special-move-list.ts`) stays a normal, fully clickable button carrying a muted inline hint, never a `disabled` one — this app's convention (confirmed via UI/UX and frontend-design expert consultation) reserves a disabled look for loading/permission states, not a domain "no data" fact, and once clicked shows a distinct, non-error status with the decode pipeline skipped entirely, never reusing the blank-frame or error status paths for a different underlying reason
- A pure helper two modules both need, where one of those modules is also imported by the other for something else (item 014's `export/gif-export.ts` needs `animation-player.ts`'s timing helpers, but `animation-player.ts` imports `gif-export.ts` to mount its own "Export GIF" buttons), is factored into its own third, dependency-free module (`animation-timing.ts`) rather than reused directly from either side — the direct-reuse shape `game-mode` already uses for these same helpers only works one-directionally; re-exported from `animation-player.ts` unchanged so every pre-existing import site is unaffected
- A GIF's one fixed logical-screen size, shared by every frame, is reconciled with an Animation whose frames reference differently-sized sprites (item 014) by compositing each frame onto one shared canvas sized to the union of every sprite's bounding box relative to its own axis (pivot) point — reusing the exact axis-offset convention `computeClsnRect`'s collision-box overlay already established — rather than sizing the canvas to the largest frame and leaving smaller ones jittering at their own native top-left
- A one-shot user action re-triggerable by a fast repeated click (an "Export GIF" click while a previous export is still encoding) is guarded by disabling the triggering control(s) for the action's duration alone, not a monotonically increasing token — unlike the sprite browser/animation player's own *continuously re-triggerable* selection decodes, a disabled `<button>` element fires neither pointer nor keyboard activation in any browser (confirmed), which is already sufficient for a single click-triggered action with no independent "supersede the in-flight one" semantics to reconcile
- A third-party library function that does its own nearest-color matching on a raw pixel buffer without an alpha-aware normalization step of its own (`gifenc`'s `applyPalette`) can assign a fully-transparent source pixel to the wrong (opaque) palette entry when that pixel's original, behind-the-scenes RGB happens to tie-distance between two candidates — found only via real-tool (Pillow) output inspection, not jsdom/unit assertions on stub calls; fixed by explicitly zeroing RGB on every alpha-0 pixel before handing the buffer to that library, removing the tie by construction (item 014, see `docs/testing.md`)

- A `<wuik-viewport>`/similar custom element's own methods (`resetToFit()`) are called through an optional-chaining guard (`el.resetToFit?.()`) rather than assumed present, since this project's test environment never registers `@openkakutou/web-ui-kit`'s custom elements against a plain `document.createElement` mount — a test asserting the call happened stubs the method directly onto the mounted element instead (item 016, ported from the identical pattern already shipped in the sibling `character-editor` repo)
- A text-bearing standalone module is retranslated on a locale change (item 018) by unsubscribing any previous `onLocaleChange` subscription at the top of its own `render*` function (a module-scoped `currentUnsubscribeLocaleChange`, torn down before a fresh one is made — same "replace, don't accumulate" idiom `main.ts`/`workspace-shell.ts` already use for their own top-level subscription) before subscribing a fresh one at the end
- A screen's status/preview line that can show either this module's own translatable text ("Loading…", a blank-frame message) or a raw WASM/bridge error is tracked with a small "kind" variable (`"loading" | "blank" | "error" | "shown"`) alongside the DOM update itself, so a locale change can retranslate only the module's own copy in place and leave a raw error untouched — recurs identically across `sprite-browser.ts`, `animation-player.ts`, `gif-export.ts`'s export controls, `animation-triggers.ts`, and `special-move-list.ts`
- A "now playing"/status line composed from more than one piece of state (item 018's `special-move-list.ts`: none/playing/stopped/selected-no-animation) is tracked as a small discriminated-union variable, recomputed by one shared render function, rather than a pre-formatted string assigned inline at each transition — the same instinct as the "kind" tracking above, needed here specifically because the underlying state (e.g. which state number was just stopped) is otherwise cleared before a later locale change could recompute the text from it
- `<wuik-tabs>` has no supported API to relabel an already-mounted tab (only an initial `slotchange`-driven build from each panel's own `label` attribute) — retranslating the sidebar's section tabs on a locale change (item 018) both updates each `<wuik-tab-panel>`'s `label` attribute (so any later, unrelated rebuild stays correct) *and* reaches directly into `<wuik-tabs>`'s shadow DOM to rewrite the already-rendered tab buttons' `textContent` by index — never removing/recreating the button, so `aria-selected` and keyboard focus survive untouched; the same reach-into-shadow-DOM technique this repo's own test suite and `MutationObserver`-on-`hidden` mechanism (decision `011`) already use for this exact component
- A pluralized sentence whose zero-count case already has its own fully separate message (item 018's palette picker: "references no external palette files" vs. "references N palette file(s)") only ever needs pluralization logic for count ≥ 1 — composed by picking an already-translated singular/plural noun and interpolating it into a translated template, never i18next's automatic plural-key suffixing, since French's own pluralization agrees with English's exact 1-vs-many boundary in that range
