# Palette picker: informational referenced-filename list, single generic external-override upload, probe-validated, single-preview re-render

**Context:** Backlog item 006 asks the user to "choose among a loaded character's available palettes" and see the currently visible sprites re-render with the new colors. This app only loads 4 required files (`.def`/`.air`/`.sff`/`.cns`) — it never has the bytes of any character-referenced `.act` palette file (`character.palettes`, a list of referenced file path strings from `.def`'s `[Files]` section). The `character` WASM bridge's `resolveSprites` can only recolor two ways: each sprite's own embedded palette (no override), or one external `.act` byte buffer applied uniformly to every sprite resolved in that call — there is no call to select an arbitrary *other* embedded palette bank without supplying real bytes for it. A `vibe:expert-ui-ux` plan consultation additionally flagged: ambiguity over whether "currently visible sprites" means a bulk thumbnail grid or a single focused preview; the risk of a stale override silently carrying over to a newly loaded character; and the need for probe-based (not just byte-length) validation.

**Decision:**
1. **`character.palettes`' referenced filenames are shown as a purely informational list** ("this character references N palette file(s): ...") — never presented as individually selectable, since selecting one cannot actually apply it (this app doesn't have its bytes). A single generic file input (`accept=".act"`) is the only way to supply a palette, independent of whether its name matches a listed one.
2. **"Currently visible sprites" means the single sprite the sprite browser's preview pane is showing, and the single frame the animation player is currently on** — not a bulk thumbnail grid, since neither screen renders more than one decoded preview at a time (confirmed against the existing code: both are single-canvas preview panes driven by a selection, not a grid of already-decoded thumbnails). No bulk-recolor loading state is needed as a result.
3. **A freshly uploaded `.act` file is validated by a real probe-resolve** against one of the loaded character's own real sprites (via the same `resolveSpritePixels` call the previews already use), not a client-side byte-length check — surfaces whatever failure reason the WASM bridge actually returns. If the character has zero sprites to probe against (degenerate case), the file is accepted optimistically with a note that it could not be pre-validated.
4. **No override state survives a character switch.** `renderApp`'s existing "each `onLoaded` re-renders every screen from scratch" behavior already guarantees this for free — the palette picker, sprite browser, and animation player all start a fresh closure with `activeOverride = null` on every newly loaded character; nothing carries the previous character's override bytes forward.
5. **An active override is surfaced by a persistent, always-visible status line in the palette picker itself** (filename + a real, keyboard-reachable, `role="status"`/`aria-live="polite"` reset button, disabled when already at default) — not duplicated into the sprite browser's or animation player's own status paragraphs, since this app has no tab/sidebar navigation yet (decisions `003`/`005`): everything renders inline on one page, so the picker's own banner stays in view alongside both consumers without a separate mechanism.

**Reason:** Each point is the narrowest design that satisfies the item's acceptance criteria against what the WASM contract actually supports, closes a concrete risk the consultation identified, or resolves a genuine ambiguity in the brief's own wording.

**Rejected alternatives:**
- **Per-filename upload prompts** (a dedicated file input per entry in `character.palettes`): rejected — implies a binding between an uploaded file and a specific embedded bank that the app cannot actually enforce or benefit from; a single generic upload is equally capable and doesn't overpromise.
- **Client-side byte-length pre-check (768/772 bytes) before probing**: rejected — a same-size non-palette file (e.g. a coincidentally-768-byte image) would pass a length check and still fail meaningfully; the real probe-resolve is the only validation that actually proves the file decodes as a usable palette.
- **Carrying an active override forward across a character switch**: rejected — the consultation's own risk analysis (silently applying a foreign palette to unrelated sprites) outweighs any convenience; resetting to default on every new load is also what the existing render architecture already does with zero extra code.
