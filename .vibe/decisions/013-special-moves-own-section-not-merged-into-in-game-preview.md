# Special Moves gets its own workspace section rather than joining item 008's In-game preview list

**Context:** Backlog item 009 adds a clickable list of the loaded character's Statedefs (States), each force-playing its associated animation, reusing item 007's playback engine the same way item 008's animation-trigger list already does. The original (now outdated) `.ux/screens/in-game-preview-section.md` spec, written before item 008 existed, described a single "in-game preview" section covering both "trigger animations live" and "one-click special moves."

**Decision:** Special Moves ships as its own sixth workspace section (`src/game-mode/special-move-list.ts`), with its own preview stage/canvas and its own `pause()` handle wired into the workspace shell's existing auto-pause-on-navigate-away convention — a near-twin of item 008's `animation-triggers.ts` rather than an addition to it. It reuses the same pure timing/decode/draw helpers item 008 already reuses from `animation-player.ts`/`sprite-browser.ts`, plus one new pure resolver (a Statedef's associated Animation, or none, since a Statedef's `anim` field can be unset (defaults to the state's own number), point at a number with no loaded animation, or hold an unevaluated trigger expression instead of a literal number — out of scope to evaluate per this item's own description).

**Reason:** Every other screen in this workspace is one concern per section (item 020's own convention; item 008 itself already carved "in-game preview" out of the debug "Animation" tab rather than merging into it), and the shell shows exactly one section at a time — so two lists sharing one canvas would only ever need to coexist visually if forced into the same panel, which nothing in the acceptance criteria requires. Merging into item 008's already-shipped, tested state machine would mean unifying two independent "which button is active" trackers (Animations vs. States) driving one shared canvas — a coordination problem invented for no user-facing benefit, and a needless regression risk to already-shipped, tested code. Keeping the new Statedef-to-Animation resolution behind a small pure function keeps the one genuinely new piece of domain logic unit-testable in isolation.

**Rejected alternatives:** Extending `animation-triggers.ts` with a second list feeding its existing playback state machine (rejected: forces one canvas to arbitrate between two independent button lists, and risks regressing item 008's own tested behavior for no acceptance-criteria benefit). Disabling/greying out list rows with no resolvable animation instead of leaving them clickable (rejected, per UI/UX and frontend-design expert consultation: a disabled control reads as broken/loading under this app's existing conventions, not "clickable but empty" — the blank-frame status pattern already used elsewhere is the better precedent, so an unresolvable State stays a normal clickable button with a muted inline hint, and shows a distinct, non-error "no animation" status only once clicked).
