# Characteristics panel's "full metadata" scope: author plus referenced file names, basenames only, palettes excluded

**Context:** Backlog item 012 asks the characteristics panel to surface the newly-available `CharacterInfo` fields the WASM contract now threads through (`character` v0.8.0, item 038): `author`, and the referenced `.def [Files]` paths (`spriteFile`, `animationFile`, `soundFile`, `commandFile`, `constantsFile`, `stateFiles`). `palettes` (referenced `.act` files) is also part of that same contract but is already displayed by the separate palette-picker screen (item 006).

**Decision:** Add an author line directly under the character name (plain text, shown only when non-empty after trimming), and a new "Files" section — styled like the existing "States" section but without a misleading `(N)` count — listing each non-empty referenced file as a labeled entry (e.g. "Sprite file: kfm.sff"), using the **basename only**, never the full path. `stateFiles` (a list) contributes one labeled row per non-empty entry. `palettes` is deliberately **not** repeated here. The whole "Files" section, and the author line, are omitted entirely (not rendered empty) when nothing qualifies.

**Reason:** UI/UX and frontend-design expert consultation converged on the same shape independently: author is prose metadata that must stay visually subordinate to the name (not another stat block), a raw list of bare filenames is meaningless without knowing which slot each fills (hence labels), full filesystem paths risk ugly overflow/wrapping in the panel's fixed width for real-world community files (hence basename-only), and repeating `palettes` here would duplicate the palette picker's own dedicated display for the same data. Omitting empty sections entirely (rather than rendering a heading with zero rows) matches the acceptance criteria's "no blank ... shown" requirement and this app's existing convention (the palette picker and sprite browser also render nothing rather than an empty shell when there's nothing to show).

**Rejected alternatives:** Showing full file paths as authored in the `.def` (rejected: real character files can carry long or directory-prefixed paths that would force awkward wrapping; the app has no use for the directory portion since it never resolves these paths against a filesystem). Repeating `palettes` in the new Files section for a single "complete" list (rejected: duplicates the palette picker's existing, more detailed display of the same data with no added value, and risks visual confusion between two "files" mentions on different screens). Keeping a "Files (N)" heading to mirror "States (N)" (rejected per frontend-design expert: the count of a fixed, mostly-empty 5-slot-plus-list structure is not a meaningful scannable number the way a State count is).
