# Localization (i18n) integration approach

**Context:** Backlog item 018 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `<wuik-locale-switcher>`, roadmap decision `023-localization-approach-for-web-ui.md`) so this app's UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads. This exact feature already shipped identically in six sibling repos (`stage-viewer-web`, `stage-editor`, `lifebar-viewer-web`, `lifebar-editor`, `character-editor`, `mode-quick-versus`); this decision ports that shape to this app's own screens — a launch screen (no chrome at all) transitioning into a persistent 6-section workspace shell.

**Decision:**
- The app's brand name ("Character Viewer") is left untranslated, a proper noun. Raw domain data — a character's own name/author, animation/sprite/state numbers, a WASM/bridge error message's own content — is never passed through translation; only the surrounding UI copy (headings, labels, buttons, status/error messages, accessible names) moves into the catalogs.
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly, under this app's own namespace (`"character-viewer-web"`) and its own `localStorage` key (`"character-viewer-web-locale"`, not `web-ui-kit`'s shared default) — every OpenKakutou web app deploys as its own GitHub Pages project site under the same origin, so sharing the default key would leak one app's language choice into every other one. Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initAppI18n` has resolved yet — the existing test suite keeps asserting plain English text unchanged without bootstrapping i18n itself.
- `initAppI18n` is only ever called from the real bootstrap (`mount()` in `main.ts`), awaited before the first `renderApp` call, which also applies the resolved locale to `document.documentElement.lang` (a small, purely additive correctness fix — this app's `index.html` currently hardcodes `lang="en"` with nothing updating it — safe to add since it changes no other test-visible behavior).
- **The `<wuik-locale-switcher>` only appears in the workspace shell's toolbar**, not the launch screen: the launch screen is deliberately full-frame with no toolbar/chrome at all (see `.ux/screens/launch-screen.md`), and the acceptance criteria's own wording ("present in the app shell") matches this literally — `<wuik-app-shell>` is only ever used by the workspace shell. The browser-detected/persisted locale still applies automatically on the launch screen via `t()`'s normal resolution; a user just can't manually switch language until a character is loaded. Confirmed via UI/UX expert consultation as an acceptable, deliberately scoped trade-off, not an oversight.
- Live locale-switching is split by how much state a re-render would otherwise destroy, per screen, the same principle every sibling app's own equivalent decision applies:
  - The characteristics panel carries no state of its own — the workspace shell's single `onLocaleChange` subscription simply re-invokes `renderCharacteristicsPanel` from the character data it already holds in closure.
  - Screens holding session-important live/async state a full re-render would destroy — the file input's per-phase status, the sprite browser's expanded groups and preview status, the palette picker's active override and upload status, the animation player's playback position/loop/collision-overlay state, the GIF export controls' encode-in-progress state, the in-game preview trigger list's active animation, the special moves list's active state — each subscribes to `onLocaleChange` internally and re-formats only its own already-shown text in place from a small stored status/kind descriptor, never a pre-formatted string, mirroring `character-editor`'s own identical `Status`-descriptor pattern. Each such module-scoped subscription is replaced (not accumulated) at the top of every render call, the same "torn down before a fresh one is made" idiom `main.ts`/`workspace-shell.ts` already use for their own top-level subscription.
  - **`<wuik-tabs>` (the vertical sidebar) has no supported API to relabel an already-mounted tab** — it only rebuilds its tab buttons' text from each `<wuik-tab-panel>`'s `label` attribute on `slotchange` (initial mount, or a panel added/removed), never on a later attribute change alone. The workspace shell's own `onLocaleChange` subscription therefore does two things together on every locale change: updates each panel's `label` attribute (the source of truth, so any future unrelated `slotchange` rebuild — e.g. if a section were ever added/removed — still reads the correct, current text) **and** reaches into `<wuik-tabs>`'s shadow DOM to rewrite the already-rendered tab buttons' `textContent` directly by index, matching the exact reach-into-shadow-DOM technique this repo's own test suite (`workspace-shell.test.ts`'s `tabButton` helper) and its `MutationObserver`-on-`hidden` mechanism (decision `011`) already use for the same component. Only `textContent` is touched — the button element itself is never removed/recreated — so `aria-selected` and keyboard focus on that exact button survive the switch untouched, confirmed via UI/UX and accessibility expert consultation as the requirement, not just a nice property.
  - The animation player's Play/Pause button and the in-game preview's/special moves list's per-item trigger buttons are retranslated the same way: only `textContent` (and, where relevant, an interpolated label) is rewritten, `aria-pressed`/`aria-current` state and focus are never touched.
  - A pluralized fragment (palette picker's "this character references N palette file(s)") is composed by picking an already-translated singular/plural noun (`palettePicker.paletteFileSingular`/`paletteFilePlural`) and interpolating it into a translated sentence template — not i18next's automatic `_one`/`_other` key-suffix pluralization — the same minimal approach every sibling app already uses. The zero-count case is its own entirely separate, dedicated sentence (`palettePicker.referencedNone`), so the noun-selection logic is only ever reached for count ≥ 1, where French pluralization agrees with English's exact 1-vs-many boundary; no French-specific zero-form is needed here.
  - A live region (`role="status"`/`aria-live="polite"`) re-announcing its already-shown text purely because a locale switch retranslated it in place (not because anything about the user's loaded data changed) is accepted as-is, not suppressed — the same trade-off every one of the six sibling apps already shipped identically for their own status regions; solving it generically would be a `web-ui-kit`-level concern, out of scope here.

**Reason:** Matching each screen's re-render strategy to how much state it owns is what keeps this feature from regressing the sprite browser's expanded-group state, the animation player's mid-playback position, the palette picker's active override, and the in-game preview/special moves list's active selection, while keeping the existing, already-large test suite passing with minimal, surgical edits — the fallback-mirrors-default-value property is what makes that possible for the large majority of existing tests. Reaching into `<wuik-tabs>`'s shadow DOM (rather than destroying and rebuilding the tab list on every locale change, which would cost the currently selected/focused tab) is the only available option given the component's own documented lack of a relabel API — the same trade-off decision `011` already made for detecting a section switch in the first place.

**Rejected alternatives:**
- *Re-run every screen's render function wholesale on every locale change, uniformly* — rejected: the sprite browser's expanded groups, the animation player's mid-playback/loop/collision-overlay state, the palette picker's active override, and the in-game preview/special moves list's active selection are exactly the state a wholesale re-render can't tell apart from a first mount, and would visibly reset or silently discard the user's current view.
- *Destroy and rebuild `<wuik-tabs>`'s child `<wuik-tab-panel>` list on every locale change, to force its own `slotchange`-driven relabel* — rejected: would reset the currently selected tab's index and drop keyboard focus, the exact regression this feature must not introduce; reaching into its shadow DOM to rewrite `textContent` in place is strictly less disruptive and keeps `aria-selected`/focus untouched.
- *A locale switcher on the launch screen too* — rejected as out of the acceptance criteria's literal scope ("present in the app shell"); the launch screen has no toolbar/chrome by design (a deliberate, already-shipped decision, not an oversight to fix here), and the browser-detected/persisted locale already applies there automatically with no manual control needed for a single, one-time step.
- *i18next's automatic `_one`/`_other` pluralization* — rejected for the fallback (pre-`initAppI18n`) path, which only does literal `{{var}}` substitution and cannot evaluate CLDR plural rules; composing a translated noun into a translated template avoids depending on an instance being active at all, matching every sibling app's own precedent.
- *Suppressing live-region re-announcement on a translation-only refresh* — rejected as a scope addition beyond what any of the six shipped sibling apps included; a generic fix (if wanted) belongs at the `web-ui-kit` level, not reinvented per consuming app.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected for the same cross-app-origin-collision reason every sibling app rejected it.
